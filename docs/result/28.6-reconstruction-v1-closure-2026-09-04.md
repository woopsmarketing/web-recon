## 2. The regression I introduced, and how it was identified

**seoultone.kr no longer reconstructs.** `pnpm reconstruct` refuses:

```
RECONSTRUCTION ERROR — route r000001 (http://seoultone.kr/) has no renderSourcePageId
```

**How the attribution was established — an A/B that the artifacts already contained**, not inference:

| observation run | `config.prepareScroll` | page `p000001` (`http://seoultone.kr/`) |
|---|---|---|
| `2026-09-02T23-12-31-237Z` | `false` | observed successfully |
| `2026-09-03T11-40-19-337Z` | `true` | `observation-error` |

Same URL, same command, one variable. The recorded error:

```
page.evaluate: Execution context was destroyed, most likely because of a navigation
phase: observe
```

**Mechanism:** the preparation scroll caused the page to navigate mid-observation, which destroyed
the JS execution context. The site spec then had 12 pages instead of 13, the root route lost its
render source, and the generator refused rather than substituting an arbitrary page.

**The engine's downstream behaviour was correct at every step** — the page recorded an error, the
spec carried the gap, and reconstruction refused instead of guessing. The bad input is mine.

**This is a generic fragility, not a seoultone property.** Any page that navigates during a scroll
loses its whole observation. `prepareScroll` must tolerate navigation: catch the destroyed-context
error, re-attach, and either retry or record `prepare-scroll-navigated` and fall back to the
unscrolled observation. **Losing the page entirely is the worst available outcome and is what
currently happens.** This is the first thing to fix in the next wave.

**How to judge this class of thing in general:** every change I make is enumerated in §1 with the
files touched; each is small enough to A/B on a single variable; and the pipeline records its own
config in `site-observation.json`, so a before/after comparison of `config` against page status
answers the question from artifacts alone, without re-running anything.

## 3. What actually stands between here and the bar

Ranked by measured impact. Full evidence in `docs/result/28.6/00-defect-ledger.md`.

**A9 — a refused recovery ships the exact tier's frozen px, and nothing checks it at any other
width. This is the top-ranked defect and it inverts a program assumption.**
"A refusal is always acceptable" does not hold: the exact tier already carries a used value measured
at 1440, so declining to emit a rule *is* shipping a wrong value. The truth check is rule-scoped and
the frozen px lives in nodes carrying no rule; and the check renders one width only, where the frozen
value is correct by construction. Gate activity: linear 2 rejections of 1699; wix-idn 0 of 341.
Arithmetic proof: linear `/pricing` @1100 clone footer right edge **1390** = `46 + 6×224` from a
refused `grid-template-columns`; linear `/` @1100 **1438** = `2 + 1436` from an unruled node.
Population on linear alone: 30 of 97 frozen-track grid containers and 3,736 of 4,567 px-width nodes
ship unrecovered.

**A12 — one site-wide tree switch, where a real site's pages disagree.** linear `/` changes between
390 and 700; `/pricing` between 1024 and 1100. One breakpoint (1025) cannot serve both, so at 1024
the clone renders linear's 390px mobile snapshot: clone `scrollHeight` is byte-identical at
390/700/1024 and again at 1100/1440 — two states, no continuum — while the source varies
continuously. This produces the `nav-link-ratio 3 of 6` BLOCKER on three routes.

**A14 / A15 / A11 — three instrument defects inflating the tally.** A route the clone never built
(HTTP 404) is graded as content loss (5 BLOCKERs on one route); a source capture that swings 4× at
one width and reverts is graded anyway (1 BLOCKER); and `overlap-excess-ratio` cannot tell a layout
collapse from a duplicated element, reading loudest when the real defect is a missing asset.
Together roughly **6 of 13** `image-presence-ratio` BLOCKERs are harness artefacts.

**A13 — the mobile probe cannot reach the tree switch on 5 of 7 sites.** Ceiling is a frozen 914;
switches are at 1025 / 1025 / 1025 / 1280 / 915. The band where the mobile tree is what actually
renders has no width evidence at all.

**Two hypotheses were REFUTED** by independent diagnosis and are recorded as E4/E5 — including one I
had relayed as fact: the wix-idn grade regression was **not** caused by shipping desktop rules, and
`recoverGridTracks` does **not** skip child-tiling verification.

`e2e` 하나가 배터리의 **46%**입니다. 이 프로그램에서 전체 또는 준전체 배터리는 **7회** 돌았고
(게이트 5회 + 최종 회귀 + 수정 후 회귀), 그것만 **약 2.5~3시간**입니다.

### 3.2 뮤텍스 직렬화

`scripts/smoke-release.ts`가 고정 픽스처 경로(`data/release-fixture.example`)를 시작과
`finally`에서 `rm -rf` 합니다. 동시 실행 시 서로의 픽스처를 파괴하므로 모든 스위트·typecheck를
`tmp/wr28/suite-lock.sh` 뮤텍스로 직렬화했습니다. 병렬 에이전트들이 락을 기다린 시간은 개별
측정하지 않았으나, 병렬 빌더 2개가 동시에 배터리를 돌릴 때마다 최소 한쪽이 20분 이상
대기하는 구조였습니다. **선행 조건 부채**로 기록합니다.

## 4. 중복 검증에 쓴 시간 — 정직한 집계

`prompt2` 검증 cadence 패치가 겨냥한 부분입니다. 이번 프로그램에서 실제로 얼마였는지:

| 항목 | 실측 |
|---|---|
| 전체/준전체 배터리 실행 횟수 | **7회** |
| 그중 소스가 실질 변경돼 정당했던 횟수 | 5회 (각 페이즈 게이트 + 최종 frozen-source) |
| **중복으로 볼 수 있는 횟수** | **2회** — 포크 수습 과정에서 양쪽 절반이 각각 게이트를 돌림 |
| 중복분 추정 비용 | **약 45~50분** |
| `e2e` 중간 게이트 제외로 절약 (사용자 승인) | Phase 7/8/9·10/11 게이트 2회 × 626초 = **약 21분** |

패치 적용 후 실제 절감은 **약 21분**이었고, 최종 회귀에서 `e2e`를 온전히 상환했습니다
(626초, 130/130, 체크 이름까지 Task-27 로그와 동일).

정직하게 덧붙이면, **줄일 수 있었던 중복의 대부분은 cadence 문제가 아니라 포크 사고 때문**
이었습니다. 검증 빈도 자체는 대체로 정당했습니다.

## 5. 검증에 쓴 시간은 낭비가 아니었다

이 프로그램에서 시간을 가장 많이 쓴 것은 적대적 검증이고, 잡아낸 결함은 전부 거기서 나왔습니다.
테스트 통과로는 하나도 잡히지 않았습니다.

|---|---|---|
| 1 | 소스 브랜드 블로커가 실제 브랜드 계보에서 무력화 (탐지기 축소) | Phase 2 검증자 |
| 2 | 핸드오프의 거짓 측정 주장 (자기 스캐너가 몇 초 만에 반증) | Phase 2 검증자 |

| 4 | 검증자 지적이 수정 없이 출하 (2회 반복, 시스템적) | 게이트 3회 |

**결정적 사실 하나:** 5번 결함이 살아 있는 동안 **2,948개 체크가 전부 통과했습니다.** 그것을
잡았어야 할 스위트에 *올바른 동작의 반대를 단언하는 체크(§3b)* 가 들어 있었기 때문입니다.
테스트 통과는 증거가 아니었고, 적대적 검증이 증거였습니다.

이 결함 하나를 잡고 고치는 데 **최종 감사 90분 + 수정 워크플로 102분 = 약 3.2시간**이
들었습니다. 전체의 10%이며, 이것이 판정을 NOT READY에서 READY로 바꾼 작업입니다.

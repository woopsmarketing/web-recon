## Text-Wrap Fix

`text-wrap-mode` and `text-wrap-style` were added together, but they are not equally load-bearing, and the verifier proved which is which rather than assuming.

Declarations are emitted in sorted name order, and `white-space` sorts *after* `text-wrap-mode`. Because `white-space` is the shorthand for `white-space-collapse` + `text-wrap-mode`, the emitted `text-wrap-mode` is overwritten. Empirical dump of a real `generateStylesheet()` call:

```
.wr-st000001{-webkit-font-smoothing:antialiased;color:rgb(0,0,0);text-wrap-mode:wrap;text-wrap-style:balance;white-space:normal}
```

`white-space` is last. `text-wrap-style` is **not** part of that shorthand, so `balance` survives — **`text-wrap-style` is the load-bearing property** (VV-05). The hazard is benign today because Chromium's computed `white-space` serialization already reflects the observed `text-wrap-mode`, so the two never disagree; it is recorded so a future change to declaration ordering is not assumed safe.

The browser-stage proof compares `Range.getClientRects()` line boxes three ways — clone against source, and balanced against plain — on a fixture pinned to `font-family: monospace` so both sides measure identical glyph metrics. Clone line-box widths are byte-identical to the source's for both the balanced and the unbalanced headline. Under the negative control the clone's `text-wrap-style` reverts to `auto` and the balanced headline collapses onto the plain one, so the assertion is not tautological.

**Field result.** 41 `text-wrap-style:balance` and 12 `:pretty` declarations in the shipped linear.app stylesheet. The visible payoff is the `/security` hero break (see *Security Findings*) and the `/changelog` heading and date columns.

## Layout-Inference Safety Fix

Two mechanisms, both refusal-only. **No CSS layout solver and no containing-block computation were built** — the module refuses where it cannot be sure.

**Containing-block guards** (`src/reconstruction/layout-inference.ts:230` `containingBlockGuard()`, computed once per node at `:422`, applied at both branches that divide by `contentAt()` — full-width at `:578` and percentage-width at `:617`):

| Reason | Trigger | Why |
|---|---|---|
| `grid-item` | parent computed `display` is `grid`/`inline-grid` | the item's containing block is its **grid area**, which no probe measured — the proven `/changelog` defect (624px item emitted as 48.75% of a 1280px parent, resolved against the 624px area, rendered 303.27px) |
| `flex-item-basis-governed` | parent flex/inline-flex, direction `row`/`row-reverse`, and `flex-grow > 0` or `flex-basis != auto` | used main-axis size comes from the flex base size grown/shrunk by free space |
| `abs-containing-block-not-parent` | `position:absolute` and the parent does not establish a containing block | the containing block is some ancestor |
| `abs-containing-block-is-padding-box` | `position:absolute`, parent *is* the containing block, but has non-zero horizontal padding or border | an abs child resolves against the parent's **padding** box, exactly the quantity `contentAt()` subtracts away |
| `fixed-position` | `position:fixed` | containing block is the viewport or a transformed ancestor — never the parent's content box |

Plus a correction that is not a guard: `contentAt()` now subtracts the parent's **border** as well as its padding (`horizontalBorder()` at `:166-190` parsing the leading length of Chromium's `<width> <style> <color>` serialization; applied at `:408-411`). That was 28.5A's fourth containing-block error.

**The failure direction is over-refusal only, by construction.** `establishesAbsoluteContainingBlock()` reads `perspective`, `will-change` and `contain`, none of which is in the Observer's `STYLE_WHITELIST`; absent reads as "does not establish a containing block", which refuses. For `position:fixed` the function is never consulted, so the transform-creates-a-fixed-containing-block case cannot leak.

**The generic proof is a two-sided one.** Part 1 of `smoke-layout-safety` drives the real `inferLayoutRules` over a generic two-column grid (296px + 624px + 360px gap inside 1280px, placeholder class names, no site strings): the grid children are refused as `grid-item`, while an **identical-arithmetic control under a block parent still recovers `width: 48.75%`** — so only the containing block can be what rejected them. Part 2 then feeds the same rules straight to the browser check, bypassing the guard, and shows Chromium rejecting them with the measurement recorded (624px observed → 304.2px rendered; 296px → 68.5px) while the exact computed fallback renders both columns within 4px of observation.

`smoke-e2e.ts:894` — "the centered `.centered` band recovered a layout rule from the probe" — passes on the real observer → compiler → generator path in every run, including the failing concurrent one, so the guards do **not** over-reject a legitimate centered container.

**Field results.** linear.app: 145 nodes refused (`grid-item` 71, `flex-item-basis-governed` 41, `abs-containing-block-is-padding-box` 17, `fixed-position` 16). stripe.com: 225 nodes refused (`grid-item` 173, `abs-containing-block-not-parent` 31, `flex-item-basis-governed` 14, `abs-containing-block-is-padding-box` 4, `fixed-position` 3). Each by-reason breakdown sums exactly to its total, confirming no double counting.

## Post-Emit Truth Verification

`src/reconstruction/layout-truth-check.ts` (new, 471 lines) serializes the reconstruction's **own** emitted desktop `RuntimeNode` tree back into static HTML inside the same `.wr-variant[data-wr-viewport=desktop][data-wr-page=…]` wrapper `PageRenderer.tsx` produces, loads it in Chromium at the page's truth viewport (1440, matching the desktop profile and `TRUTH_WIDTH`) with the app's real generated stylesheet plus one empty `<style id="wr-layout-candidates">`, and aborts every `http://**` and `https://**` route so the render is offline and deterministic. It measures each candidate's `[data-wr-node]` rect with the candidate tier **empty** — the baseline, i.e. what the exact computed fallback alone renders — then swaps only that style element's text and re-measures. No navigation, no re-parse; each extra round costs one reflow. It is wired at `generate-app.ts:232`, before the generated stylesheet is written, so it is on the real `pnpm reconstruct` path, the QA-correction path (`apply-corrections.ts:119`) and the E2E path.

**The guarantee, stated exactly.** A candidate is rejected when `max(|dx|,|dwidth|)` against the observed truth rect exceeds 4px **AND** exceeds the baseline error by more than 0.5px. The first half says the rule is wrong; the second says the *rule* — not the reconstruction's own unavoidable drift from absent images and substituted fonts — is what made it wrong. Therefore:

> **An accepted rule renders no worse than the exact-computed fallback it overrides, +0.5px, at the truth viewport.**

That is the whole claim. It is **not** "truth-accurate within 4px": a rule whose node lands arbitrarily far from the observed box still ships whenever the exact-computed baseline was equally far. The verifier observed this live — a `width: 101%` fixture (observed 600, rendered ~505) shipped, correctly, because it was no worse than baseline. `acceptedRegressed = 0` is a real confirming re-render over exactly the surviving rules (`:576-585`), and it must be read as "no accepted rule regressed in the render that accepted it".

**The correction that mattered (D3).** The first verification found that a status of `no-candidates` was also returned when candidates existed but none were checkable, and that every candidate then shipped **unverified**. The correction split the status into six values and closed the per-rule leak by computing survivors from the *checkable* set:

| Status | Geometry that ships |
|---|---|
| `verified` | only measured survivors |
| `no-candidates` | zero candidates existed |
| `responsive-hidden-only` | none — every candidate was `responsive-hidden`, accepted unchecked |
| `unverifiable-candidates` | none — all rejected |
| `chromium-unavailable` | none — all rejected (previously they shipped unverified) |
| `disabled` | all — the caller's explicit opt-out, and the only such path |

The re-verifier walked every early return, throw site and the `finish()` accounting line by line and confirmed the invariant on all eleven enumerated paths: **a geometry-affecting recovered rule never ships unverified**. `grep` across `src/` and `scripts/` finds **no caller** that sets `verifyLayout: false`; the only `enabled: false` in the tree is the suite testing the `disabled` status itself.

`rejectedUnverifiable` is *derived* (`:378` — `geometry.length − shipped.size − rejectedByTruthCheck`, where `shipped` is built from the same array that produces the emitted CSS), so it cannot be hand-maintained out of agreement with what ships. The three counters partition `geometry` exactly.

**Accepting `responsive-hidden` unchecked is sound, and the proof survived the refactor.** `hiddenRanges()` opens a band at the floor-midpoint between a hidden width and its lower *visible* neighbour and closes it at the floor-midpoint minus 0.02 against its upper visible neighbour; the emission site is gated on the node being visible at 1440. With `LAYOUT_PROBE_WIDTHS = [390, 768, 1024, 1440, 1920]`, no generated band can apply at the truth viewport.

**Determinism.** Two `generateApp()` runs over a 4-page / 6-candidate corpus **with** candidates produced 23 files each, 23/23 sha256-identical, with byte-identical counters. `elapsedMs` is returned to the caller and never written to the manifest. (A double generation on a *full probed corpus* remains an open carry-forward.)

**Cost.** A synthetic page of 6,000 element nodes with 400 candidate rules (200 deliberately regressing) verified in 460 ms end to end including Chromium launch. Pages with no candidates launch nothing.

**Compatibility.** Every new manifest field is `z.optional()`. All 34 historical `reconstruction-manifest.json` files under `data/` parse through the current schema with every 28.5B field absent.

**Two counters, two denominators.** The manifest's `rejectedByGuard` counts **nodes** a containing-block guard refused *before any rule was emitted* — sourced from `plan.layout.counters.guardRefusals`, incremented at the two refusal sites, each immediately followed by `continue`, so the node never enters `candidateRules` at all. `candidateRules` counts **rules** inference proposed. Summing the two is a category error; they are sequential stages over different populations, not overlapping axes. The **rule ledger reconciles exactly** in both runs:

- linear: `truthCheckable 1019 + acceptedUnchecked 738 = candidateRules 1757`; `1757 − rejectedByTruthCheck 5 = acceptedRules 1752 = recoveredRules`; `rejectedUnverifiable 0`.
- stripe: `726 + 0 = 726`; `726 − 25 = 701`; `rejectedUnverifiable 0`.

## Video Asset Honesty

`video` was added to `PRIMARY_IMAGE_KINDS` (`src/reconstruction/asset-resolver.ts:37`) so a `<video>`'s own media asset is eligible to become its `src` at all — it never was before. `MEDIA_ASSET_KINDS` (`:60-63`) is derived as `PRIMARY_IMAGE_KINDS ∪ SRCSET_KINDS`, so the media-kind set cannot drift from what `choosePrimary()`/`buildSrcSet()` actually consume.

**This is a RENDER change, not merely an accounting change** — the first verifier caught the build handoff's framing and the re-verifier re-measured it independently: **26 of the corpus's 30 `<video>` elements get a different `src` under the shipped resolver** than under the pre-28.5B ordering (14 that previously emitted no `src` at all now emit their real media URL; 12 that previously emitted their *poster image* URL as `<video src>`, undecodable as video, now emit the real media URL). Both are strict improvements, and both mean downstream visual baselines shift.

**The honesty invariant** — no missing or unmaterializable `<video>` can coexist with `unresolvedElementAssets = 0` — was established through a ten-row truth table measured through the **real** `AssetResolver.resolve()` and the **real** `compileNode()`, not reasoned about:

| Shape | Counted at | Count |
|---|---|---|
| a. `<video>` with resolvable video-kind src | nowhere | 0 |
| b. `<video>` with a dangling assetRef | resolver | 1 |
| c. `<video>` poster-only (src still renders the poster, unchanged) | resolver, via `videoContentUnresolved` | 1 |
| d. `<video>` + all-resolvable `<source>` children | nowhere | 0 |
| e. GAP-A: `<video>` + 2 `<source>` children, one with **zero** assetRefs | the broken `<source>` child, exactly once; parent zero | 1 |
| f. GAP-B: `<video>` with only a background-image ref + good `<source>` children | nowhere | 0 |
| g. `<video>` with only a background-image ref and no children | `compile-node` | 1 |
| h. bare `<video>`, no refs, no children | `compile-node` | 1 |
| i. `<img>` with zero assetRefs (regression control) | resolver | 1 |
| j. `<picture> > <source>` with zero assetRefs (new behaviour) | the `<source>` element | 1 |

**The counting point** is the `<source>` element itself, never also the parent: a `<source>` exists for exactly one purpose, so zero assetRefs *is* its failure, observable without sibling context. `compile-node.ts` therefore deliberately leaves a `<video>` uncounted whenever any `<source>` child exists — the child carries the count. Case (j) is correct honesty rather than a false positive: `collect-assets.ts` pushes an asset ref for every resolvable http(s) URL, so zero refs means no URL was recoverable and the clone genuinely renders no media there.

## Per-Viewport Custom Properties

The change that needed two corrections, and the one whose *reach* was the real question.

**Storage and emission.** Custom properties are captured per viewport into an `.optional()` field on `ViewportObservationSchema` and carried verbatim onto `ViewportPageSpec`. Nothing merges, dedups or diffs desktop against mobile. Emission is scoped, not `:root`:

```
[data-wr-page="pNNNNNN"][data-wr-viewport="desktop|mobile"] { --name: value; }
```

`PageRenderer` renders both observed viewports into **one** document as sibling `.wr-variant` divs, so there is a single `:root` for two viewports and a per-viewport difference would be unrepresentable. The block is emitted **first** in the generated stylesheet (`generate-app.ts:230`), before the computed-style classes, so every rule below and every `var()` surviving inside captured inline-SVG markup resolves against it. Caps are 500 names / 200 chars, and are never silent (`discoveredCount`, `countCapped`, `valueCappedCount`, over-long values dropped rather than truncated). Names go through `/^--[-A-Za-z0-9_]*$/` with case **preserved**; values through the existing `isSafeCssValue`; `pageId`/`viewportId` through `/^[A-Za-z0-9_-]+$/` before reaching a selector string. A hostile probe (4 hostile values, 1 hostile name, 1 hostile pageId) had all six rejected **and counted**, with the survivor in the same scope still emitted and brace balance intact.

**The reach story — 0 → 135 → 151, and 0/16 → 16/16.** The first verification's verdict was `PASS_WITH_RISKS` on a MATERIAL finding: on the actual pilot site the shipped discovery emitted **nothing**. 30 of linear.app's 84 stylesheets are readable; the other 54 throw on `.cssRules` because the CSS is served cross-origin from `static.linear.app`. Broadening the selector filter did not help either — the 155 names reachable in `document.styleSheets` are declared on component selectors and none resolve on the document element. The site's real tokens lived in cross-origin sheets plus one `document.adoptedStyleSheets` the code never walked.

- **Correction 1** walked `document.adoptedStyleSheets` with the same visitor (`collect-dom.ts:986-987`), plus three under-report fixes: recursion into a style rule's own `cssRules` for CSS nesting and `CSSNestedDeclarations`, case-insensitive `:root`/`html` matching, and an explicit `unresolvedCount` for names discovered but not resolving. Measured on live linear.app with the **real** shipped collector via `page.evaluate`: **0 → 135 names**, all resolving, no cap hit. But the 16 distinct names its 239 inline SVGs reference through 183 `var()` calls were disjoint from those 135, so the 28.5A inline-SVG consumer defect stood at **0/16**.
- **Correction 2** added reference-driven discovery: every `var(--name)` token is extracted from each captured `<svg>`'s `outerHTML` and resolved **at the consuming element** via `getComputedStyle(svgRoot)`. Precedence rule: **sheet wins** (a name already discovered from a stylesheet keeps its root-resolved value, and the overlap is counted in `referenceSheetKnownCount`). Conflict rule: **first consuming element in document order wins**, with every later differing resolution counted in `referenceResolutionConflicts`. Result on live linear.app: **151 names, 16/16 SVG var names covered**, `referenceUnresolved` 0, `referenceConflicts` 0. That is 16 of 16, not the 11 forecast — element resolution additionally reaches 5 locally-scoped names (`--hero-line`, `--icon-color`, `--label-faint`, `--plan-icon-car`, `--plan-icon-robot`) that `documentElement` gives nothing for.

**Independent replication and a mutation test.** The final re-verifier reproduced the live numbers **exactly** — 151 names, sheet-discovered 135, `svgNamesCovered` 16, every counter matched to the unit — and then mutated the reference-discovery loop bound to `i < 0`: `smoke-custom-properties` dropped **92/92 → 80/92**, with all 12 failures inside §8 including the two real-Chromium paint checks, which fell back to `rgb(0,0,0)`. Sections §1–§7 all still passed under the mutation, isolating the failures to the mechanism under test. The file was restored byte-identically (sha256 `1117abd8…` before and after) and the suite returned to 92/92. Determinism was proven on two axes: two full fresh-context collector runs over a deterministic fixture, and two evaluates within one live linear.app load — byte-identical both times.

**Field result, and it is load-bearing rather than cosmetic.** The linear run emits 16 blocks / 2,676 declarations / 0 rejected across 8 routes × 2 viewports. The auditor parsed the two `p000001` viewport blocks out of the 11.9 MB stylesheet and diffed them key by key: each carries 151 properties and **9 genuinely differ** — `--sx-1ele6il` `1px` vs `0.5px` (a DPR-3 hairline), `--sx-15wwovl` `#28292e` vs `#303136`, `--sx-1ikf7kw` `#ffffff22` vs `#ffffff45`, `--sx-9pdekr` `#8f9197` vs `#b5b7bd`, and five more. A same-value-twice emission would have been indistinguishable from a working one in the counters.

**Named limitations.** Discovery is `:root`/`html` selector parts, adopted sheets at the **document** level only (not shadow roots), and inline-SVG `outerHTML` references. `style` attributes, pseudo-element content and observed computed values are out of scope. Precedence is keyed on *discovered* rather than *kept* names (C2), which can lose a value the consuming element would have resolved — zero occurrences on linear.app, and counted rather than silent.

## @1 vs @16 vs dE76

`@1` — the historical `changedPixelRatio` — counts any pixel where any channel differs by ≥ 1/255. 28.5A proved it misleading: on `/pricing` desktop it read 0.383053 while `@16` read 0.021063, i.e. **94.5% of the headline was sub-perceptible**. Change 6 left `@1` byte-for-byte unchanged for artifact continuity and added two channels beside it.

- **`@16`** (`screenshot-diff.ts:82,216`): fraction of overlapping pixels where the **max** channel delta is ≥ 16/255 — a per-pixel max, not a sum or an average; boundary 16 counts, 15 does not. This is the primary visible-regression channel.
- **ΔE76** (`:96` sRGB→linear LUT, `:111` `labF`, `:116` `srgbToLab`, `:130` `deltaE76`): real CIELAB, implemented in-repo with no new dependency, reported as `>2.3` (just-noticeable difference), `>10` (clearly different side by side), plus mean and max.

**The math was validated independently twice**, not accepted. The first verifier wrote an exact-constant reimplementation: red↔green 170.584201 vs 170.584201 (absolute difference 0.0); black↔white 100.000001 (1.42e-14); red↔blue 176.332724 (2.84e-14); grey 200↔208 2.878117 (0.0). The final auditor separately checked against published CIELAB references: `Lab(white) = [100, 0.005, −0.010]`, `Lab(black) = [0,0,0]`, `Lab(red) = [53.23, 80.11, 67.22]` against an expected `[53.24, 80.09, 67.20]`, `Lab(green) = [87.74, −86.18, 83.18]` exact. This is real CIELAB, not a renamed RGB distance.

**Adversarial properties checked.** No path produces NaN or Infinity across zero-overlap, height-mismatch, fully-transparent and 50%-alpha cases. Both sides are composited over white with the *same* unchanged function before differencing, so alpha can never be read as a colour difference. The ΔE76 short-circuit (skip when `pixelMax === 0`) is provably sound: bit-identical composited channels map to the identical Lab triple, so ΔE76 is exactly 0 and the skip changes no reported value. Worst-case cost on a 1440×30000 (43.2 MP) pair where every pixel differs is 2,846 ms — a ~10× slowdown, bounded and affordable.

**How to read the numbers in this report.** Read `@16` and ΔE76>10. `@1` alone overstates: on `/pricing` desktop it falls 0.3914 → 0.0266 while the amplitude-gated `@16` falls only 0.0295 → 0.0158, because a large area moved a tiny, near-threshold amount in the old clone. Conversely, on `/changelog` the metrics *understate* the win, because text occupies a small share of a 36-megapixel page — see *Changelog Findings*.

**Not fixed, not claimed fixed, and preserved as evidence for 28.5C.** The residual handoff states this in its own header: `notClaimedFixed: true`, and "this sweep does NOT fix anything and does NOT claim anything is fixed."

Method: the hardened app served from a verbatim `tmp/` copy (`data/` never written to), 8 routes × 8 widths (390, 500, 700, 914, 1024, 1100, 1440, 1920), viewport height 900, DSF 1, `isMobile: false` on both sides at every width, using the project's own capture path and unmodified diff module. `/pricing` and `/changelog` additionally got a live-source counterpart at all 8 widths.

**The 391–914 dead zone: same defect, not worse, not improved.** All 8 of 8 routes produce a frozen band spanning 390..914 in which `scrollHeight`, `visibleNodeCount`, `displayNoneCount` and `visibleTextLength` are **bit-identical**. On 5 routes even `maxContentRight` is constant; on the other 3 the only thing that changes is the far edge of a full-bleed element tracking the canvas — the content column never moves. `<main>` stays at its observed 390px width at 500, 700 and 914 on all 8 routes (deficits 110 / 310 / 524px) while the live source's `<main>` tracks the viewport exactly. `/pricing` clone `scrollHeight` at 914 is 7,714 against a live 6,990; 28.5A measured 7,712 vs 6,990, a 2px difference attributable to source drift. **Numerically unchanged.**

**The 1024–1231.98 pricing band: same defect, sharpened, not reduced.** `/pricing` clone `displayNoneCount` goes 240 (1440) → 743 (1024 and 1100) — 503 extra nodes hidden against 28.5A's 507 — and `visibleNodeCount` drops 1,706 → 1,035 (−39.3%). Visible text falls from 2,675 characters at 1232 to 2,351 at 1100, i.e. **286 characters lost** against the source's 2,637 at the same width (28.5A: 274). The band's **lower** edge at 1024 is approximately correct — the live source is also in its narrow layout there. The residual handoff explicitly refuses to bank this as progress: "This is a sharper description of the SAME defect, not a reduction of it — at 1100 the visible loss is total (3 of 4 columns plus the header row)."

**The mechanism is intact in the shipped artifact.** All **738** `@media` blocks in the generated stylesheet are at the single synthetic band `(min-width: 1024px) and (max-width: 1231.98px)`; the sheet contains no other breakpoint. `app/globals.css` adds the variant switch (`[data-wr-viewport='desktop']` hidden under `max-width: 914.98px`, `mobile` hidden under `min-width: 915px`), whose 915 breakpoint is **inferred** as the midpoint of the two observed endpoints, not observed. 28.5A counted 710 blocks with 709 at the same band. Wave 1 did not remove, narrow or widen this mechanism.

**Fidelity across widths.** `/pricing` clone-vs-source `@16` by width: 390 0.0371, 500 0.0387, 700 0.0446, 914 0.0376, 1024 0.0378, 1100 0.0430, **1440 0.0158**, **1920 0.0125**. Note the shape: a *too-tall* failure at 914 and a *too-short* failure at 1024 exist within 110px of each other.

**Four honesty notes carried into 28.5C.** (1) Horizontal overflow is partly real: at 390 the live source *also* overflows (`/pricing` source `maxContentRight` 1280.47 vs clone 1288.79); the clone-specific part is that this overflow persists unchanged to 914 while the source snaps to the viewport. (2) `/customers` and `/customers/automattic` get *shorter* when the desktop variant engages — legitimate variant switches, not content deletion, though they trip the 25% scrollHeight-cliff rule. (3) The live source's own `/changelog` scrollHeight is non-monotonic across widths (a lazily-populated feed measured without scrolling), so height deltas there carry real source noise. (4) `/customers` reports exactly 24 console errors at **every** width — 12 cross-origin CORS-blocked customer-logo SVGs — width-invariant, therefore an asset-independence residual, not a responsive one.

## Why We Are Not Switching To Preserved Stylesheets Yet

28.5A ran the experiment properly and the answer has not changed. Variant B — source DOM plus preserved source stylesheets plus self-hosted assets, no JS — wins **decisively on linear.app**: `@16` 0.0016 on `/security` and 0.0002 on `/pricing` against the accepted artifact's 0.0381 and 0.0295, i.e. 24× and 148× better at a perceptible threshold, with `scrollHeight` exact on 6/6 pairs including 390 and 1920 rendered from a single 1440 capture.

Four reasons that result is not adoptable:

1. **It does not generalise.** The same harvest/build/offline-serve/compare pipeline on six other sites, each scored against its own live-vs-live noise floor: vercel.com 0.0598 (30× its floor), github.com/features/actions 0.0858 (21×), tailwindcss.com 0.0926 (62×), stripe.com 0.1230 (615×), lit.dev 0.2593 (∞), developer.mozilla.org 0.2673 (∞). **Best of six is 33× worse than linear.app.** Shadow DOM is a hard wall for `outerHTML` (76 and 28 shadow hosts on the two worst; `commonAreaRatio` 0.8956 and 0.8923), and JS-driven canvas paint is untouched by stylesheet preservation.
2. **The good numbers depend on a stack-specific quirk that occurred on none of the six.** styled-components v6 in production inserts rules via CSSOM into an *empty* `<style data-styled="active">` node, which serialises as 0 bytes in `outerHTML`; restoring linear.app's fidelity requires re-injecting 61 rules / 7,202 bytes on `/security` and 78 / 9,490 on `/pricing`. `emptyStyleWithRules = 0` on all six other sites.
3. **The naive form is measurably worse than what we ship today, and it fails silently.** `outerHTML` only, no CSSOM harvest: `/security` 0.0535 `@16` and `/pricing` 0.0360 `@16` against the accepted artifact's 0.0381 and 0.0295 — with no error, no console warning and no failed request. An `h1` ablation shows the mechanism: 64px live and in the full variant, **16px** in the naive one.
4. **It discards the product.** A switch would gut the IR and with it regenerability, 9,929 slot bindings, named nodes, theme tokens and content-injection accounting — the entire authoring surface Tasks 18–25 were built on.

28.5A's own honest hole applies and is repeated here: nobody re-ran the *current* pipeline on those six sites, so this is a measured challenger against an unmeasured incumbent on the generalisation axis. Wave 1's answer is the one 28.5A recommended — **adopt the mechanism findings, reject the architecture swap** — and it is now supported by a second data point: the six generic changes did generalise to stripe.com in one run, with 0 regressions.

Notably, Wave 1 adopted one finding *from* the preservation experiment: `document.adoptedStyleSheets`, which 28.5A found was a member of neither `document.styleSheets` nor `outerHTML` and was referenced nowhere in `src/`, is exactly what took custom-property reach from 0 to 135 on linear.app.

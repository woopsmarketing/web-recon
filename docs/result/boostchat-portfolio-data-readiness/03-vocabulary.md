# 03 — category / scope / keywords 어휘, 사용자 표현 커버리지

## 1. category (`categories.json`, 4종, 모두 사용 중)

| id | name | 프로젝트 |
|---|---|---|
| full-remodel | 전체 리모델링 | bi-01, bi-02, bi-03, bi-05, bi-07 |
| kitchen-bath | 주방·욕실 리뉴얼 | bi-04 |
| move-in-styling | 입주 전 홈스타일링 | bi-08 |
| partial-remodel | 부분 리모델링 | bi-06 |

- 한/영 혼재: id는 영문 kebab, name은 한국어다. 식별자와 라벨이 분리된 일관된 패턴이라 문제는 아니다.
- **동의어**: "리뉴얼"과 "리모델링"이 사실상 같은 뜻이다(bi-04 title "리뉴얼", summary "부분 리뉴얼").
- **계층 누락**: kitchen-bath는 의미상 partial-remodel의 하위 유형인데 taxonomy는 평면·단일값이다. 사용자가 "부분 리모델링"이라고 하면 type 필터로는 bi-06만 나오고 bi-04가 빠진다(keyword "부분"으로는 두 건 모두 나온다).
- **자유 텍스트 검색의 맹점**: `keywordHaystack`은 title·summary·location·scope·keywords만 읽고 **category name을 읽지 않는다**(`project-filter.ts:338-342`). 그래서 keyword "전체 리모델링"은 3/5(bi-01, bi-05, bi-07)만 찾는다. bi-02와 bi-03은 summary에 "전체"가 없어서 빠진다. 이 표현은 반드시 type(category)으로 매핑해야 한다.
- 매핑되지 않는 사용자 동의어: 올수리 / 풀리모델링 / 전체 공사 / 전체 인테리어 → full-remodel, 부분 수리·부분 공사 → partial ∪ kitchen-bath, 홈스타일링·스타일링 → move-in-styling. "입주 인테리어"는 **모호**하다(입주 전 전체 리모델링과 홈스타일링 양쪽으로 쓰인다) → 되물어야 한다.

## 2. scope (34 entries, 20종)

| 문제 | 사례 |
|---|---|
| 세분도 불일치 | 욕실(bi-01·02·07) vs 공용 욕실 / 안방 욕실(bi-04). 침실(bi-02·05·07) vs 안방 / 작은방(bi-01), 안방(bi-08), 아이방(bi-03) |
| `·` 복합 토큰 | 현관·중문(bi-01, bi-06), 주방·팬트리(bi-03), 주방·다이닝(bi-05), 거실·다이닝(bi-07). "주방" exact 매칭은 bi-03·bi-05를 놓친다. |
| 구분자 차이 | 같은 bi-01 안에서 scope는 "복도 수납"(공백), gallery 그룹은 "복도·수납"(가운뎃점)이다. |
| scope ↔ gallery 그룹명 불일치 | bi-01: scope "현관·중문 / 안방 / 작은방 / 복도 수납" vs 그룹 "현관 / 침실 / 복도·수납". 방 어휘 체계가 두 개다. |
| 필드 의미가 카테고리마다 다름 | bi-08(styling)의 scope "거실/다이닝/안방/서재"는 시공이 아니라 스타일링(아트월·조명·커튼·가구) 범위다. |
| 공간 단위만 있고 공종 단위가 없음 | 도배, 바닥, 샷시, 확장, 전기·조명, 철거 같은 **공종**은 표현할 수 없다. 확장 발코니(bi-05)만 공간 이름으로 들어가 있다. |
| 제외·경미 작업은 body에만 있음 | bi-03 "욕실은 그대로", bi-05 "욕실 실리콘·수전만 교체", bi-04 "바닥과 도배는 그대로" → scope에는 나타나지 않는다(scope에서 제외된 것 자체는 일관적이다). |

- 한/영 혼재: 없다(전부 한국어). 철자 변형: 공백 vs `·` 1건.
- 결론: scope 자체는 "~만" 질의에 쓸 수 있을 만큼 **망라적(exhaustive)**으로 적혀 있다. 다만 방 이름 정규화(분해 + 상하위 관계)가 없으면 exact 비교가 실패한다. 증거: naive 부분집합 → 0건, 정규화 후 → bi-04.

## 3. keywords (23 entries, 8종)

| keyword | 프로젝트 | 서술 텍스트 근거 |
|---|---|---|
| 화이트 | bi-01, 02, 04, 06, 07 | 있음(5/5) |
| 미니멀 | bi-01, 06, 07 | bi-07 title만 |
| 모던 | bi-03, 04, 08 | **0/8. 어느 텍스트에도 없다** |
| 간접조명 | bi-01, 06, 08 | 있음 |
| 수납 특화 | bi-01, 03, 07 | 있음("수납") |
| 내추럴 | bi-02, 05 | 있음 |
| 우드 포인트 | bi-02, 05 | 있음(오크) |
| 그레이지 | bi-03, 08 | 있음 |

- 철자 변형·한영 혼재: keywords 필드 안에는 없다(전부 한글 외래어/한국어, 표기 일관). 사용자 입력(white, modern, 모던한)과는 어긋난다.
- **facet 혼재**: 색·톤(화이트, 그레이지), 스타일(모던, 미니멀, 내추럴), 기능(간접조명, 수납 특화), 소재 포인트(우드 포인트)가 한 목록에 있다. ProjectFilter의 `style` 그룹은 8개 전부를 "스타일"로 취급한다.
- **태깅 불완전(태그가 없다고 속성이 없는 게 아님)**:
  - bi-05: summary가 "밝은 오크와 **웜 화이트**"인데 `화이트` 태그가 없다.
  - bi-01: 고객 인용에 "**우드 포인트** 덕분에"가 그대로 있고 "오크"가 3회 나오는데(body 1회 "오크 니치", gallery alt 2회) `우드 포인트` 태그가 없다.
  - bi-08: 월넛 가구가 있는데 우드 계열 태그가 없다(경계 사례).
- **근거 없는 태그**: `모던`은 순수 큐레이션 태그다. 텍스트로 교차검증하거나 "왜 모던인지" 설명할 근거가 없다.
- **정규화 없이 쓰면 조건이 조용히 사라진다**: `normalizeProjectFilter`는 어휘에 없는 값을 **그냥 버린다**(`project-filter.ts:300-321`). style "모던한"이나 "화이트톤"을 넣으면 조건이 빠지고 **8건 전부**가 반환된다. 증거: `evidence/project-filter-probe.txt`. NL 파서가 어휘 밖 토큰을 내면 "0건"이 아니라 "전체"가 나온다.

## 4. 사용자 표현 → 현재 데이터 표현력

| 사용자 표현 | 데이터상 표현 | 커버 | 표현 가능성 |
|---|---|---|---|
| "화이트톤" | keyword `화이트` 5건. 텍스트 "화이트톤"은 bi-01 한 건뿐이고, 웜 화이트 bi-05는 태그 없이 텍스트에만 있다. | 태그 5/8, 텍스트 포함 6/8 | **가능.** "톤" 접미사 제거 / 하얀·흰·white 동의어가 필요하다. literal keyword "화이트톤"은 bi-01만 찾는다. |
| "모던" | keyword `모던` 3건(bi-03, 04, 08) | 3/8, 텍스트 근거 0 | **부분.** 태그는 있지만 정의가 없고 근거 텍스트가 없다. 미니멀·화이트·그레이지와의 경계가 정해지지 않았다. |
| "미니멀" | keyword `미니멀` 3건(bi-01, 06, 07) | 3/8 | **가능**(태그 기준). 사용자 변형 "깔끔한/심플/정돈"은 literal 0/8("정돈"은 bi-01 body, "단정"은 bi-06 body)이라 동의어 매핑이 필요하다. |
| "전체 리모델링" | category name "전체 리모델링" = full-remodel 5건 | 5/8 | **가능.** 단 type으로 매핑해야 한다. 자유 텍스트 검색은 3/5만 찾는다. |

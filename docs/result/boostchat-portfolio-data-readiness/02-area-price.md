# 02 — area / pricePerArea

## 1. area

| 항목 | 결과 |
|---|---|
| pyeong / m2 혼재 | **구조화 필드에는 없다**: 8/8 `pyeong`. 자유 텍스트에서는 bi-01 body 한 곳에만 "공급면적 약 34평, 전용면적 약 84㎡"로 두 단위가 함께 나온다. |
| basis 분포 | supply **8** / exclusive 0 / unknown 0 (모두 명시값, 기본값 의존 없음) |
| 숫자 형식 | 전부 양의 정수(19~51)다. 소수·문자열·0은 없다. title과 slug의 "N평"이 area.value와 8/8 일치한다. |
| 이상치 | 없다. 51평(bi-08)이 최대지만 신축 대형 평형이라 정상 범위다. |
| 평형 버킷 (`AREA_SCALES.pyeong`) | 20평 미만 1 (bi-07) · 20평대 2 (bi-02, bi-05) · 30평대 3 (bi-01, bi-04, bi-06) · 40평대 1 (bi-03) · 50평 이상 1 (bi-08) |

**평형 질의는 안전하다.** 한국 주거 맥락에서 "34평"은 관례상 공급면적이고, schema도 이 관례를 코드로 둔다(`schema.ts:101-111` `defaultAreaBasis`: ko + residential + 평 → `supply`). 데이터도 8/8 supply이므로 "34평", "30평대", "24평"은 변환 없이 그대로 비교된다.

**㎡ 질의는 안전하지 않다.**
- `ProjectFilterRecord.area`는 `{ value, unit }`만 가진다. **basis를 버린다**(`project-filter.ts:74`).
- `areaIn`은 basis와 무관하게 1평 = 400/121 ㎡로 환산한다(`project-filter.ts:114-118`). 그래서 34평(공급)은 112.40㎡가 된다.
- 사용자가 말하는 "84㎡ / 84타입 / 국평"은 보통 **전용면적**이다. 84㎡를 그대로 환산하면 25.41평, 즉 20평대 버킷이 되어 bi-02·bi-05와 매칭된다. 의도는 34평형(bi-01·bi-06)인데 다른 결과가 나온다.
- 이 사이트는 `areaScale: "pyeong"`이라 UI에서는 환산이 일어나지 않는다. 하지만 BoostChat이 ㎡ 표현을 파싱하는 순간 이 문제가 발생한다.
- 전용면적은 bi-01 body 텍스트에만 있다(1/8).

## 2. pricePerArea

| 항목 | 결과 |
|---|---|
| coverage | **6/8 (75%)**. 없는 2건은 bi-04(kitchen-bath)와 bi-06(partial-remodel)이다. 전체 공간 프로젝트는 6/6에 있고, **부분 공사는 0/2**다. |
| currency / unit | KRW 6/6, pyeong 6/6. area.unit과 같은 단위라 환산 없이 곱셈·비교가 가능하다. |
| 값 | 160만(bi-08 styling), 240만, 260만, 270만, 290만, 320만. 전부 10만 원 단위다("평당 N만 원"으로 렌더). |
| 분포 | full-remodel n=5: 240만~320만, 평균 276만, 중앙값 270만. styling n=1: 160만. |
| 이상치 | 통계적 이상치는 없다(n이 작음). 160만은 **카테고리 차이**이지 이상치가 아니다. schema는 개연성(plausibility)을 판단하지 않는다고 명시한다(`schema.ts:188-191`). |
| price 버킷 (`krw-pyeong`) | 평당 180만 원 미만 1 (bi-08) · 180–250만 1 (bi-02) · 250–300만 3 (bi-05, bi-07, bi-01) · 300–350만 1 (bi-03) |

### area와 안전하게 비교 가능한가

- **산술적으로는 가능하다**: 단위(pyeong)와 통화(KRW)가 같다.
- **의미적으로는 조건부다**:
  1. pricePerArea에는 basis 필드가 없다. 가격이 공급평 기준이라는 것은 area.basis=supply와 **같다고 가정할 뿐** 어디에도 적혀 있지 않다.
  2. 평당가 × 평수로 구한 총액(5,130만~1억 3,440만)은 **파생 추정치**이지 기록된 계약 총액이 아니다. VAT, 가구·가전(특히 styling bi-08은 가구·커튼 포함 추정), 철거·확장 포함 여부가 정의되어 있지 않다.
  3. 부분 공사의 "평당가"는 정의부터 모호하다(집 전체 평수 기준인지, 시공 면적 기준인지). 2건이 비어 있는 것은 이 모호성 때문으로 보인다.
  4. 카테고리가 다르면 비교할 수 없다(styling 160만 vs remodel 240만~320만).
- 결론: **같은 카테고리(full-remodel) 안의 상대 비교**만 안전하다. 총액 추정은 "추정" 라벨을 붙인 참고치로만 쓸 수 있다.

### 예산(총액) 질의와의 관계

- 데이터에 총액 필드가 없다. ProjectFilter의 price 차원도 **평당가 버킷만** 지원한다(`project-filter.ts:172-184`).
- 총 예산을 평당가로 바꾸려면 사용자 평수로 나눠야 한다. 예: 2천만 ÷ 24평 = 83.3만/평 → "180만 미만" 버킷 → 20평대 결과는 0건(`evidence/project-filter-probe.txt`).
- 값이 없으면 price 조건에 절대 매칭되지 않는다(`project-filter.ts` 헤더: "A missing value never matches"). 그래서 소액 예산에 맞을 가능성이 가장 큰 **부분 공사 2건이 가격 검색에서 보이지 않는다**.

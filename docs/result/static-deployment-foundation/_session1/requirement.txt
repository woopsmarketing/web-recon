========================================
C. STATIC DEPLOY CONTRACT
========================================

현재 실제 Site Build Package를 다시 조사한다.

예:

data/site-builds/<siteId>/
  current.json
  previous.json
  history.jsonl
  packages/<buildInputId>/
    build-record.json
    site/**

정확한 실물을 기준으로 한다.

다음 contract를 정의한다.

Publish input:
- siteId
- exact build-record
- QA PASS
- packageHash
- site/ directory

Artifact identity:
- packageHash

Target conceptual layout:

sites/<siteId>/packages/<packageHash>/...

routing/<hostname>.json

단 실제 package route mapping과
static export의 파일 구조를 조사한 뒤 확정한다.

기존 package를 재구성하거나 변형하지 않는다.

========================================
D. site:publish CLI
========================================

web-recon repo 안에 publish CLI를 구현한다.

예시 명령:

pnpm site:publish --site boost-interior-demo --host <hostname>

정확한 CLI style은 기존 repo convention을 따른다.

역할:

1. site/build 입력 검증
2. build-record schema validation
3. QA PASS 확인
4. packageHash 재검증
5. package file inventory
6. content-type 결정
7. R2 target key 계산
8. 이미 동일 immutable artifact가 존재하면 안전하게 skip 가능
9. package 전체 upload
10. upload verification
11. 모든 artifact 성공 후에만 routing pointer 전환
12. 실패하면 기존 live pointer 유지

중요:

partial upload 후 pointer가 바뀌면 안 된다.

순서:

UPLOAD IMMUTABLE PACKAGE
→ VERIFY
→ SWITCH POINTER

이어야 한다.

가능하면:

--dry-run

을 구현한다.

dry-run은:
- R2 write 없음
- pointer write 없음
- 실제 업로드 예정 파일/key/content-type/cache-policy 출력

========================================
E. recon-runtime
========================================

아주 작은 Cloudflare Worker를 구현한다.

책임:

Host
+
pathname

→ routing pointer resolve

→ immutable package object resolve

→ R2 GET

→ HTTP response

절대 하지 않는 것:

- Next server
- React SSR
- Supabase query
- LLM
- site editing
- build
- publish
- arbitrary API

지원:

/
clean URLs
nested pages
assets
_next/static
404.html

현재 static export의 실제 파일 layout을 기준으로
/path → R2 object mapping을 정확하게 구현.

directory/index.html인지
foo.html인지 추측하지 말고
실제 package를 조사한다.

========================================
F. CACHE / SEO DELIVERY
========================================

cache 정책 설계/구현:

Hashed immutable assets:
long-lived immutable cache

HTML:
packageHash가 content namespace가 되도록 설계
새 package publish가 옛 package bytes를 변경하지 않음

정확한 Cloudflare Worker Cache API 사용 여부는
현재 Worker/R2 환경을 조사해 최소 구조를 택한다.

필수:

- correct Content-Type
- correct 404 HTTP status
- HEAD 가능 여부 검토
- redirect/canonical을 Worker가 임의로 만들지 않음
- HTML에 존재하는 SEO metadata를 변형하지 않음
- byte serving이 deterministic

BoostChat script/widget은 이번 작업에서 추가 금지.

========================================
G. CLOUDFLARE CONFIG AS CODE
========================================

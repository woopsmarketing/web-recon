--------------------------------------------------

- never report success when navigation cannot be safely attempted

- avoid overengineering because mailto is transitional

provide honest fallback.

- show configured email
- offer a copyable prepared message
- do not claim inquiry was sent

==================================================
14. PUBLICATION ATOMICITY
==================================================

Hard invariant:

UPLOAD
→ VERIFY
→ ACTIVATE

Never:

ACTIVATE
→ finish upload

Publication flow:

1. inspect build
2. validate build record
3. validate QA
4. recalculate/verify package identity where possible
5. enumerate files
6. upload immutable package
7. verify package
8. write/switch routing pointer last

If any step before 8 fails:

current live pointer remains unchanged.

If pointer write fails:

old publication remains live.

Rollback:

pointer swap to an existing retained package.

Do not delete previous package during publish.

==================================================

MUTABLE POINTER

IMMUTABLE PACKAGE OBJECTS
